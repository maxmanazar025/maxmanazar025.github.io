Express.js'da JWT va RBAC: CareTrack tajribasi

Tibbiy ma'lumotlar bilan ishlaydigan API'da "kim kirdi?" va "unga nima mumkin?" — ikki xil savol. Ularni ikki xil middleware hal qiladi.

Maxmanazar Sultonov·25 Noy 2026·6 daq o'qish

CareTrack Clinic — shifokorlar, bemorlar va kasalliklarni boshqaradigan REST API. Bu yerda xavfsizlik ikki qatlamdan iborat: autentifikatsiya (sen kimsan?) va avtorizatsiya (senga bu amal mumkinmi?). Ularni aralashtirmaslik — toza va tekshirsa bo'ladigan kodning kaliti.

1. Login: bcrypt va qisqa muddatli token

Login endpoint'i email va parolni oladi, parolni bcrypt hash bilan solishtiradi va muvaffaqiyatli bo'lsa 24 soatlik JWT qaytaradi. Token ichida faqat kerakli minimum: id, email, role, full_name. Parol hash'i hech qachon javobga kirmaydi.

Muhim detal: "email topilmadi" va "parol noto'g'ri" holatlarida bir xil javob qaytadi — "Email yoki parol noto'g'ri". Aks holda hujumchi qaysi email'lar ro'yxatdan o'tganini bilib oladi.

2. authenticateToken: 401

export function authenticateToken(req, res, next) {
  const token = req.headers['authorization']?.split(' ')[1]; // "Bearer <token>"
  if (!token) return res.status(401).json({ error: 'Token topilmadi.' });

  jwt.verify(token, JWT_SECRET, (err, user) => {
    if (err) return res.status(403).json({ error: "Noto'g'ri yoki muddati o'tgan token." });
    req.user = user;   // keyingi middleware'lar uchun
    next();
  });
}

Bu middleware faqat bitta ishni qiladi: tokenni tekshiradi va req.user'ni to'ldiradi. Rollar haqida hech narsa bilmaydi.

3. authorizeRoles: 403

export function authorizeRoles(...allowedRoles) {
  return (req, res, next) => {
    if (!req.user) return res.status(401).json({ error: 'Avtorizatsiya talab qilinadi.' });
    if (!allowedRoles.includes(req.user.role))
      return res.status(403).json({ error: `Ruxsat etilmagan amal. Rolingiz: ${req.user.role}` });
    next();
  };
}

Bu — higher-order function: rollar ro'yxatini oladi va middleware qaytaradi. Natijada route'lar o'qilishi oson, deklarativ bo'ladi:

router.delete('/:id', authenticateToken, authorizeRoles('admin'), deletePatient);
router.get('/',       authenticateToken, authorizeRoles('admin', 'doctor'), listPatients);

4. 401 va 403 — farqi nima?

  • 401 Unauthorized — "seni tanimayman". Token yo'q yoki yaroqsiz. Klient qayta login qilishi kerak.
  • 403 Forbidden — "seni taniyman, lekin bunga ruxsating yo'q". Qayta login yordam bermaydi.

Frontend shu kodlarga qarab harakat qiladi: 401'da login sahifasiga yo'naltiradi, 403'da "ruxsat yo'q" xabarini ko'rsatadi. Shuning uchun muddati o'tgan token uchun ham 401 qaytarish to'g'riroq — keyingi versiyada shuni tuzataman.

5. Ikki tilli xatolar

Har bir xato javobida error (o'zbekcha) va error_en (inglizcha) maydonlari bor. Klinika xodimi o'z tilida o'qiydi, integratsiya qiluvchi dasturchi esa ingliz tilida.

6. Production'dan oldingi checklist

O'quv loyihasidan production'ga o'tishda o'zimga qo'ygan qoidalar:

  • Sir kalitga default qiymat bermang. process.env.JWT_SECRET || '...' — xavfli: env o'rnatilmay qolsa, server hamma biladigan kalit bilan ishlayveradi. To'g'risi — kalit yo'q bo'lsa, server ishga tushmasin.
  • .env faylini hech qachon commit qilmang — .gitignore'ga qo'shing va .env.example bering. Agar tasodifan push qilingan bo'lsa, kalitni almashtiring.
  • 500 xatoda err.message'ni klientga qaytarmang — u ichki tuzilma haqida ma'lumot beradi. Log'ga yozing.
  • Login endpoint'iga rate limit qo'ying — parol tanlashga qarshi.
Xavfsizlik — bu funksiya emas, bu odat. Har bir route'ni yozganda ikki savol: "kim?" va "nimaga ruxsat?"
